第7章：File Pointers 机制

本章目标
  • 理解 File Pointers 的设计动机
  • 掌握 File Pointers 的三种类型
  • 了解文件生命周期管理策略
  • 理解上下文注入的技术实现

7.1 问题的起源

在多 Agent 系统中，上下文管理是一个核心挑战。

想象一个没有 File Pointers 的场景：

  • Agent A 读取了文件 F1、F2、F3
  • Agent B 需要读取 F2、F4、F5
  • 问题来了：Agent B 怎么知道 F2、F4、F5 在哪里？内容是什么？

传统方案：

  1. 把所有文件都传给 Agent（浪费 token）
  2. 让 Agent 自己搜索文件（不可靠）
  3. 手动复制粘贴（繁琐且容易出错）

Scriptorium 选择了第四种方案：File Pointers。

7.2 什么是 File Pointers？

File Pointers 本质上是一个精确的文件路径清单：

📖 需要读取的文件：
  - source-map.md          ← 项目内部文件
  - outline.md             ← 项目内部文件
  - agents/01-orchestrator.md  ← 源码文件

📝 需要输出的文件：
  - output/research/ch03-report.md

类比：就像餐厅的点菜单——不是把整个厨房都端给服务员，而是给他一张列有所需食材的清单。

7.3 File Pointers 的三种类型

Scriptorium 定义了三种文件类型，每种有不同的生命周期：

7.3.1 静态文件（Static Files）

特点：一旦创建，绝不修改。

示例：

  • outline.md（大纲）
  • style-guide.md（写作规范）
  • glossary.md（术语表）

为什么静态？

  • 避免"版本混乱"
  • 确保所有 Agent 引用的是同一版本
  • 防止引用冲突

7.3.2 只追加文件（Append-Only Files）

特点：只能追加，不能修改历史内容。

示例：

  • checkpoint.md（进度追踪）
  • 审查报告 reviews/chXX-*.md
## 历史记录

### 2026-04-08 10:00
- 完成第3章初稿

### 2026-04-08 14:00
- R1 审查完成，发现 2 个问题

7.3.3 可覆盖文件（Overwritable Files）

特点：每次更新都是全量覆盖。

示例：

  • 章节草稿 chapters/draft/chXX-draft.md
  • 章节摘要 chapter-summaries.md
# 第3章草稿
[这是最新的完整版本，覆盖了旧版本]

7.4.2 为什么上下文注入重要？

1. Token 成本控制

  • Agent 上下文窗口有限
  • 精确的文件列表避免"信息过载"
  • 只传递必要的文件

2. 可靠性保证

  • Agent 不需要自己"猜"文件在哪里
  • 主编排确保引用的文件都存在
  • 减少"找不到文件"错误

3. 可审计性

  • 每次调度的 File Pointers 都有记录
  • 可以回溯"这个决策是怎么来的"
  • 便于问题排查

7.5 File Pointers 的设计原则

7.5.1 最小化原则

只传递 Agent 必须的文件，不传递"可能有用的"文件。

✅ 正确做法❌ 错误做法
传递 ch03 相关的 3 个文件传递所有 50 个文件
传递当前章节的 style-guide传递所有历史版本的 style-guide

7.5.2 精确性原则

文件路径必须精确到文件名，不能模糊引用。

✅ 正确做法❌ 错误做法
agents/01-orchestrator.mdagents 目录下的文件
第 15-30 行中间某一段

7.5.3 版本隔离原则

不同 Agent 操作不同类型的文件，避免冲突。

Agent操作的文件类型
主编排静态文件、只追加文件
研究员源码文件（只读）、研究报告
作家可覆盖文件（草稿）
R1/R2/R3只追加文件（审查报告）

7.6 File Pointers 的实际应用

7.6.1 主编排的调度模板

主编排在调度每个 Agent 时，都会生成相应的 File Pointers：

## Agent #3 研究员 调度

### 读取文件（Read）
- output/memory/source-map.md      ← 源码定位
- output/memory/outline.md          ← 大纲要求
- agents/01-orchestrator.md        ← 主编排规范
- framework/file-pointers.md       ← 本章主题

### 输出文件（Write）
- output/research/ch03-report.md   ← 研究报告

7.6.2 三审并行的 File Pointers

R1、R2、R3 虽然同时审查同一份草稿，但它们的 File Pointers 不同：

审查员读取的文件
R1ch03-draft.md + 源码文件（根据草稿中的引用）
R2ch03-draft.md + glossary.md + metaphor-registry.md
R3ch03-draft.md + style-guide.md

7.7 小结

本章我们深入了解了 File Pointers 机制：

  1. 问题起源：多 Agent 系统的上下文管理挑战
  2. 核心概念：精确的文件路径清单
  3. 三种类型：静态文件、只追加文件、可覆盖文件
  4. 上下文注入：精确控制 Agent 的输入输出
  5. 设计原则：最小化、精确性、版本隔离

File Pointers 是 Scriptorium 的核心创新之一——它解决了"谁读什么文件"的问题，让多 Agent 协作变得可控和可审计。
