第8章：审查架构与质量保障

本章目标
  • 理解三层审查架构的设计哲学
  • 掌握质量问题的分级与处理策略
  • 了解审查报告的结构与格式
  • 理解如何通过流程设计预防质量问题

8.1 质量不是事后检查出来的

很多项目的质量保障策略是：

  1. 写代码
  2. 测试
  3. 发现问题，打补丁
  4. 重复步骤 2-3

结果是：质量债务越积越多，后期维护成本爆炸。

Scriptorium 采用了质量内建（Quality Built-in）策略：

flowchart LR subgraph "传统模式" T1["写"] --> T2["测"] T2 --> T3["改"] T3 --> T2 end subgraph "质量内建模式" Q1["设计阶段"] --> Q2["执行阶段"] Q2 --> Q3["验证阶段"] Q3 --> Q4["交付阶段"] end style Q1 fill:#c8e6c9 style Q4 fill:#c8e6c9

8.2 三层审查架构

Scriptorium 的质量保障分为三个层次：

flowchart TB subgraph "第一层：单章审查" L1["每章完成后"] --> R1["R1 代码审查"] L1 --> R2["R2 一致性审查"] L1 --> R3["R3 内容审查"] end subgraph "第二层：读者验证" L2["每批完成后"] --> P["读者评审团"] end subgraph "第三层：全局审计" L3["全书完成后"] --> A["Phase 4 统稿审计"] end R1 --> M1["合并报告"] R2 --> M1 R3 --> M1 M1 --> P P --> A style L1 fill:#e3f2fd style L2 fill:#fff3e0 style L3 fill:#fce4ec

8.2.1 第一层：单章审查

每写完一章，立即进行 R1/R2/R3 三审。

优点：

  • 问题发现早，修复成本低
  • 及时反馈给作家，避免错误固化
  • 保持写作节奏

8.2.2 第二层：读者验证

每批（3章）完成后，进行读者评审团验证。

优点：

  • 验证"可理解性"而非"正确性"
  • 从读者视角发现审查员忽略的问题
  • 分批验证，避免全书完成后才发现根本性问题

8.2.3 第三层：全局审计

所有章节写完后，进行全书的系统性审计。

优点：

  • 发现跨章一致性问题
  • 验证全书叙事连贯性
  • 最终质量把控

8.3 质量问题的分级

不是所有问题都同等重要。Scriptorium 定义了四个严重级别：

级别标记含义处理策略
致命错误🔴会导致误导或完全无法理解必须修复才能进入下一阶段
严重错误🟠影响阅读理解，但可推测应该修复
一般问题🟡不影响理解，但不够精确建议修复
轻微问题⚪优化建议，非强制可选择性修复

8.3.1 级别判定示例

同一段代码引用错误：

场景级别原因
函数名写错🔴 致命读者按书操作会失败
变量名写错🟠 严重读者会困惑，但能猜到
注释文字不准确🟡 一般不影响代码执行
空格多少⚪ 轻微完全不影响

8.4 审查报告的结构

每个审查员产出的报告都有统一的结构：

# 第3章 R1 代码审查报告

## 审查概要
- 审查员：R1 源码审查员
- 审查时间：2026-04-08
- 审查结论：⚠️ 需修改（2个致命问题）

## 统计信息
| 类型 | 数量 |
|------|------|
| 代码引用总数 | 5 |
| 发现问题 | 3 |
| 🔴 致命 | 1 |
| 🟠 严重 | 1 |
| 🟡 一般 | 1 |

## 问题列表

### 问题 #1：函数名错误
- **级别**：🔴 致命
- **位置**：第 3 章，第 42 行
- **描述**：草稿写的是 `handleRequest(req, res)`，但源码中是 `handle(req, res)`
- **影响**：读者按书操作会失败
- **建议修复**：将 `handleRequest` 改为 `handle`

### 问题 #2：文件路径不存在
- ...

## 附录：审查的文件清单
- agents/01-orchestrator.md
- framework/workflow.md
- output/chapters/draft/ch03-draft.md

8.5 主编排的审查协调

主编排在审查环节扮演"质量协调员"的角色：

flowchart TB subgraph "主编排协调" O["主编排 #0"] -->|"调度"| R["R1/R2/R3"] R -->|"产出"| RPT["审查报告"] RPT -->|"汇总"| M["合并报告"] M -->|"分析"| D["决策"] D -->|"反馈"| W["作家"] W -->|"修改"| DRAFT["新草稿"] DRAFT -->|"再审"| R end style O fill:#fff9c4 style M fill:#e3f2fd

8.5.1 主编排的决策逻辑

当收到三份审查报告后，主编排需要决策：

情况 1：所有审查通过

→ 章节标记为"待发布"
→ 启动下一章写作

情况 2：有致命/严重问题

→ 将问题反馈给作家
→ 要求修改草稿
→ 修改后重新审查

情况 3：有一般/轻微问题

→ 可选择：
  A. 要求修改（保守策略）
  B. 接受当前版本（激进策略）

8.5.2 修复-审查循环

Scriptorium 允许无限次修复-审查循环，直到质量达标：

flowchart LR D["草稿"] --> R["审查"] R -->|"通过"| E["结束"] R -->|"不通过"| F["修改"] F --> D style R fill:#ffebee
设计哲学

宁可慢一点，也要确保质量。修复-审查循环没有次数限制，直到所有致命和严重问题都解决。

8.6 预防胜于治疗

除了审查，Scriptorium 还通过流程设计预防质量问题：

8.6.1 写作前的规范

Phase 2 共享资源的目的就是预防：

  • style-guide.md → 防止格式混乱
  • glossary.md → 防止术语不一致
  • metaphor-registry.md → 防止比喻冲突

8.6.2 写作中的约束

作家在写作时会收到明确的约束条件：

  • 每章必须包含至少 2 个代码示例
  • 代码示例必须标注文件路径
  • 每个核心概念必须至少 1 个比喻
  • 段落长度不超过 5 行

8.6.3 写作后的验证

每个草稿在提交前会自动检查：

  • 是否包含 <!-- DRAFT_COMPLETE --> 标记
  • 字数是否符合 3000-5000 字要求
  • 是否引用了所有必要的文件

8.7 质量指标追踪

Scriptorium 在 checkpoint.md 中追踪每个章节的质量状态：

章节R1R2R3读者评审综合状态
ch01✅✅⚠️⬜进行中
ch02✅✅✅⬜待读者评审
ch03🔴✅✅✅需修改

8.8 小结

本章我们了解了审查架构与质量保障体系：

  1. 三层审查架构：单章审查 → 读者验证 → 全局审计
  2. 质量问题分级：🔴致命 → 🟠严重 → 🟡一般 → ⚪轻微
  3. 审查报告结构：概要 → 统计 → 问题列表 → 附录
  4. 主编排协调：汇总报告、决策、反馈、循环
  5. 预防策略：规范、约束、自动化验证

质量不是事后检查出来的，而是通过流程设计内建到每个环节中的。
