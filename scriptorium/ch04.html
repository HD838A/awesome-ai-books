第4章：创作 Agent 团队

本章目标
  • 理解研究员的"源码考古学家"角色
  • 理解作家的"畅销书作者"角色
  • 掌握两者的协作流程
  • 了解 Agent 类型的设计意图

4.1 流水线上的两把刷子

如果说主编排是"总导演"，那么研究员和作家就是流水线上的两把刷子——一把负责"研究"，一把负责"写作"。

为什么不是一个人既研究又写作？

类比：就像拍纪录片，实地采访的记者和后期剪辑的导演往往是不同的人。记者擅长发现故事，导演擅长讲故事。专业分工让各自做自己最擅长的事。

4.2 研究员 #3：源码考古学家

4.2.1 角色定位

研究员就像一个考古学家——他深入代码的"遗址"，挖掘设计决策的"文物"，发现隐藏的"彩蛋"。

核心职责：

职责说明
深度源码调研对指定章节覆盖的源码文件进行逐行级别的分析
设计决策提取发现代码背后的架构决策、权衡取舍
关键细节发掘找出巧妙的技巧、反直觉的设计
知识图谱构建梳理概念、函数、模块间的依赖关系

4.2.2 研究员的工作产出

研究员产出的是调研报告，而非最终章节：

# 第3章 调研报告：主编排的秘密

## 核心发现

### 发现1：主编排的核心职责
- **位置**：`agents/01-orchestrator.md:15-30`
- **意义**：主编排是唯一贯穿全流程的 Agent

### 发现2：File Pointers 机制
- **位置**：`framework/file-pointers.md`
- **意义**：精确的上下文注入是框架的核心创新

## 设计决策

### 决策1：为什么主编排是"用户自己"？
- **选择**：不把主编排做成子 Agent
- **推测原因**：避免"谁来调度调度者"的问题

4.2.3 研究员的质量标准

研究员不是简单地"复制粘贴"代码，而是：

  • ✅ 标注精确的文件路径和行号
  • ✅ 解释设计"为什么"这么做（而不仅仅是什么）
  • ✅ 标记每个发现在书中的讲解意义
  • ✅ 构建清晰的概念关系图
类比
研究员就像美食评论家——他不只是描述"这道菜用了番茄和鸡蛋"，而是分析"为什么要用番茄炒而不是红烧"。

4.3 作家 #4：畅销书作者

4.3.1 角色定位

作家就像一个技术布道师——他要把枯燥的源码分析转化为引人入胜的技术叙事。

核心职责：

职责说明
章节撰写将源码分析转化为技术叙事
风格统一遵循 style-guide，保持全书一致
知识衔接参考 chapter-summaries，避免重复
术语规范使用 glossary 中的标准术语
比喻管理复用/避免冲突 metaphor-registry

4.3.2 写作的艺术

作家的工作不是简单地把研究报告"翻译"成中文，而是：

4.3.3 作家必须遵守的规范

style-guide 规定的硬性要求：

规范要求
章节字数3000~5000 字
代码示例每章必须有，标注文件路径和行号
比喻密度每个核心概念至少一个比喻
段落长度不超过 5 行
开头风格用场景、故事或问题引入
结尾风格总结要点 + 承上启下

4.4 协作流程

4.4.1 标准流水线

主编排调度
    │
    ▼
研究员 #3 读取：
  - source-map.md（源码定位）
  - outline.md（本章要求）
  - 源码文件
    │
    ▼ 产出调研报告
    │
作家 #4 读取：
  - 调研报告
  - style-guide.md
  - glossary.md
  - metaphor-registry.md
  - chapter-summaries.md
    │
    ▼ 产出章节草稿
    │
主编排审查

4.4.2 File Pointers 传递

研究员接收到的 File Pointers：

📖 读取：
  - output/memory/source-map.md      ← 源码文件定位
  - output/memory/outline.md         ← 本章大纲要求
  - 源码文件（按 source-map）        ← 实际源码

📝 输出：
  - output/research/ch04-report.md

作家接收到的 File Pointers：

📖 读取：
  - output/research/ch04-report.md   ← 本章调研报告
  - output/memory/style-guide.md      ← 写作规范
  - output/memory/chapter-summaries.md ← 前序章节摘要
  - output/memory/glossary.md         ← 术语表
  - output/memory/metaphor-registry.md ← 比喻表

📝 输出：
  - output/chapters/draft/ch04-draft.md

4.4.3 为什么不是并行？

有人问：研究员在研究 A 章时，作家可以同时写 B 章吗？

可以，但有限制：

并行示例（3章/批）：

第1周：
  - 研究员研究 ch04
  - 作家写 ch01（基于上周的 ch01-report）

第2周：
  - 研究员研究 ch05
  - 作家写 ch02（基于上周的 ch02-report）

依此类推...

限制：

  • 每批内部，研究员和作家仍是流水线关系
  • 不同批次之间可以并行
  • 建议批次大小：3 章

4.5 Agent 类型的设计

4.5.1 两种 Agent 类型

Scriptorium 定义了两种 Agent 类型：

类型说明适用 Agent
explore探索型，适合深度分析、代码调研研究员、R1、R2
general-purpose通用型，适合综合任务主编排、作家、架构师

4.5.2 为什么需要区分？

类比：医院的科室分类

  • 专科医生（explore）→ 深度诊断某个器官
  • 全科医生（general-purpose）→ 综合评估整体健康

explore 类型擅长：

  • 逐行分析代码
  • 深度挖掘设计意图
  • 穷举式探索

general-purpose 类型擅长：

  • 综合决策
  • 平衡多方需求
  • 处理模糊任务

4.6 小结

本章我们认识了流水线上的两把刷子：

  1. 研究员 #3：源码考古学家，负责深度调研和设计决策提取
  2. 作家 #4：畅销书作者，负责将源码分析转化为技术叙事
  3. 协作流程：研究员产出报告 → 作家产出草稿
  4. Agent 类型：explore 适合深度分析，general-purpose 适合综合任务
