第1章：认识 Scriptorium

本章目标：理解 Scriptorium 是什么、解决什么问题；掌握框架的核心设计理念；了解框架的适用场景和基本使用流程

1.1 一句话介绍

想象一下，你组织了一个"虚拟编辑部"——里面有技术总监、畅销书作家、资深编辑、美食评论家（试读评审），甚至还有一个负责排版的设计师。但这些"人"不是真正的员工，而是 AI Agent。它们各司其职、分工协作，最终帮你完成一本技术书籍的写作。

Scriptorium 就是这样一套框架——它让多个 AI Agent 像编辑部一样协作，覆盖从大纲设计到最终出版的全流程。

1.2 解决什么问题

1.2.1 AI 写作的常见困境

用 AI 写技术书籍，最大的问题是"幻觉"——AI 会自信地编造代码细节、API 参数、甚至函数名。这在技术写作中是致命的错误。

传统的解决方案是"人肉校对"——写完后找专家逐行审核。但这违背了用 AI 提效的初衷。

Scriptorium 的思路完全不同：不让 AI 凭"记忆"写作，而是让它精确引用源码文件作为事实来源。

1.2.2 长文本的上下文丢失

AI 的上下文窗口是有限的。写完第 5 章后，AI 可能已经"忘记"第 1 章用了什么术语、某个概念怎么定义的。

Scriptorium 用外部文件系统作为"大脑"。每一步的上下文都精确注入，Agent 每次被调用时都像是刚入职的新员工，通过读取文件来了解项目情况。

1.2.3 多章节的一致性

一本书有 10 章，作者 A 写前 5 章，作者 B 写后 5 章。术语翻译可能不一致，比喻可能冲突，数据可能对不上。这些"一致性"问题在大项目中尤为突出。

Scriptorium 的解决方案是共享资源机制：

  • glossary.md（术语表）——统一术语翻译
  • metaphor-registry.md（比喻注册表）——防止跨章比喻冲突
  • source-map.md（源码地图）——统一数据来源

1.3 适用场景

Scriptorium 专为以下场景设计：

  • ✅ 源码阅读系列的技术书籍（如《某某框架源码深度解析》）
  • ✅ 逐章拆解大型代码仓库的架构分析
  • ✅ 面向多层次读者的技术科普
  • ✅ 需要流程可控的长篇技术写作项目

不适用：

  • ❌ 纯理论教材（没有源码可分析）
  • ❌ API 参考文档
  • ❌ 短篇技术博客

1.4 核心设计理念

1.4.1 Agent 是无状态的，文件系统是有状态的

这是 Scriptorium 的第一原则。

每个 Agent 每次被调用时都是"新人"——它不记住上次做了什么，所有的"记忆"都存储在共享文件系统中。这带来两个关键优势：

  1. 可重现：任何时候都可以从 checkpoint 恢复
  2. 可追踪：文件的修改历史就是 Agent 的工作日志

1.4.2 Hub-Spoke 架构

Scriptorium 采用轴辐式（Hub-Spoke）架构：

graph TB H["主编排 #0
Hub"] --> S1["架构师 #1"] H --> S2["读者代言人 #2"] H --> S3["研究员 #3"] H --> S4["作家 #4"] H --> S5["审查员 R1/R2/R3"] H --> S11["装帧工人 #11"] style H fill:#e1f5fe classDef spoke fill:#fff3e0 class S1,S2,S3,S4,S5,S11 spoke

主编排（Hub）是唯一的中枢，所有的子 Agent（Spoke）只与主编排通信，子 Agent 之间不直接对话。这确保了：

  • 信息流向单一，容易追踪
  • 无环形依赖，调度逻辑清晰
  • 每个 Agent 的职责边界清晰

1.4.3 File Pointers：精确的上下文注入

每个 Agent 被调用时，主编排传递的不是"让它自己决定读什么"，而是精确的文件路径列表——这就是 File Pointers 机制。

类比一下：演员不需要知道其他演员在演什么，导演只需要给他一张"提词卡"，告诉他该读哪些剧本片段。

1.5 五阶段工作流

Scriptorium 的生产流水线分为 5 个阶段：

阶段名称主要产出
Phase 1大纲定稿outline.md（章节大纲）
Phase 2共享资源构建glossary.md、metaphor-registry.md 等
Phase 3逐章写作章节草稿 + 审查报告
Phase 4统稿审计全书一致性检查
Phase 5装帧发布可阅读的 HTML 电子书

1.6 Agent 团队一览

Scriptorium 的团队有 12 个 Agent：

管理团队：

  • #0 主编排：掌握全局进度的责任编辑
  • #1 架构师：设计书籍大纲的技术总监
  • #2 读者代言人：从读者视角提需求的产品经理

执行团队：

  • #3 研究员：深入源码考古的考古学家
  • #4 作家：撰写章节正文的畅销书作者
  • #11 装帧工人：把 Markdown 变成漂亮 HTML 的排版设计师

审查团队：

  • R1 源码审查员：较真每一行代码的考据专家
  • R2 一致性审查员：揪出跨章矛盾的记忆管理员
  • R3 内容审查员：把控可读性的资深编辑
  • RS/RE/RH 读者评审团：分别模拟大学生、工程师、科技爱好者三视角

1.7 快速开始

1.7.1 一句话启动

把这句话发给任何兼容 Scriptorium 的 AI 编程助手：

我的项目源码在 /path/to/project。请读 QUICK_START.md，然后向我提问。
没有问题就开始你的工作。

AI 会自动完成：

  1. 读取框架文档
  2. 向你确认基本信息（书名、目标读者等）
  3. 自主运行全部 5 个阶段
  4. 交付可阅读的 HTML 电子书

1.7.2 中断后恢复

写作过程中断？告诉 AI：

请读 output/memory/checkpoint.md，继续上次未完成的工作。

Scriptorium 会自动从 checkpoint 恢复进度。

1.8 小结

本章我们认识了 Scriptorium——一个让多个 AI Agent 协作写作技术书籍的框架。它的核心设计理念可以概括为三点：

  1. 文件系统是唯一的事实来源——所有 Agent 通过共享文件传递信息
  2. Hub-Spoke 架构——主编排作为唯一中枢协调所有 Agent
  3. 五阶段流水线——从大纲到出版，流程清晰可控
