2.1 架构设计理念

2.1.1 为什么要用 Hub-Spoke？

想象一个传统的编辑部：作者、编辑、校对之间可以直接对话，甚至可以在茶水间闲聊。这种模式在人类协作中没问题，但对 AI Agent 来说，直接对话会带来上下文污染——每个 Agent 都要处理来自其他 Agent 的"噪音"。

Scriptorium 的解决方案是轴辐式（Hub-Spoke）架构：

graph TB subgraph Hub["主编排 #0（Hub）"] O["调度中心"] end subgraph Spokes["Agent 团队（Spokes）"] A1["#1 架构师"] A2["#2 读者代言人"] A3["#3 研究员"] A4["#4 作家"] R1["R1 源码审查"] R2["R2 一致性审查"] R3["R3 内容审查"] end O --> A1 O --> A2 O --> A3 O --> A4 O --> R1 O --> R2 O --> R3 style O fill:#e3f2fd,stroke:#1976d2 classDef spoke fill:#fff3e0,stroke:#ff9800 class A1,A2,A3,A4,R1,R2,R3 spoke

主编排（Hub）是唯一的中枢，所有子 Agent（Spoke）只与主编排通信。类比一下：就像地铁网络，中央换乘站连接所有线路，但各站之间不直通。

2.1.2 架构优势

优势说明
无环依赖信息流单向，不会出现"A等B，B等A"的死锁
故障隔离单个 Agent 失败不影响其他 Agent
可观测性所有调度决策集中在主编排，便于日志和调试
职责清晰每个 Agent 只知道自己该做什么，不知道其他 Agent 在做什么

2.2 无状态 Agent 设计

2.2.1 Agent 是无状态的，文件系统是有状态的

这是 Scriptorium 的第一原则。

类比：想象你每次上班都变成一个"失忆的新员工"。你不记得上次做了什么、客户是谁、项目进度到哪了。但你的办公桌上有一叠文件（通过 File Pointers 传递），里面记录了所有你需要知道的信息。

sequenceDiagram participant H as 主编排 participant A as Agent participant F as 文件系统 H->>A: 调度 Agent，传递 File Pointers Note over A: "你是个新人" A->>F: 读取输入文件 F-->>A: 返回上下文 A->>A: 执行任务 A->>F: 写入产出物 Note over A: "任务完成，Agent 失忆退出"

2.2.2 为什么这样设计？

  1. 可重现：任何时候都可以从 checkpoint 恢复
  2. 可追溯：文件的修改历史就是 Agent 的工作日志
  3. 可替换：任何 Agent 实例都可以被同类型的新实例替换

2.2.3 与微服务架构的类比

Scriptorium 的设计哲学与现代微服务架构惊人地相似：

微服务概念Scriptorium 实现
服务无状态Agent 无状态
数据库存储状态文件系统存储状态
消息队列通信File Pointers 通信
API 网关编排主编排调度

2.3 File Pointers 机制

2.3.1 什么是 File Pointers？

File Pointers（文件指针）是主编排在调度 Agent 时传递的精确文件路径列表。

这不是简单的"让 Agent 自己决定读什么"，而是主编排精心挑选的文件组合——每个 Agent 只看到它完成任务所需的最小信息集。

主编排传递给作家 Agent 的 File Pointers 示例：

📖 读取文件：
   - output/memory/style-guide.md      ← 写作风格要求
   - output/memory/glossary.md         ← 已有术语定义
   - output/memory/metaphor-registry.md ← 已用比喻（避免重复）
   - output/research/ch02-report.md     ← 本章源码分析报告
   - output/memory/chapter-summaries.md ← 前序章节摘要

📝 输出文件：
   - output/chapters/draft/ch02-draft.md

2.3.2 File Pointers 的三大功能

功能说明
注入上下文告诉 Agent 需要读取哪些文件来获取"记忆"
指定输出告诉 Agent 需要将成果写入哪个文件
隔离职责不同 Agent 只看到与自己职责相关的文件

2.3.3 遵循最小权限原则

每个 Agent 只获得完成当前任务最少量的文件引用：

作家 #4 的 File Pointers（需要读取）：
  ✅ style-guide.md        ← 必须，写作规范
  ✅ glossary.md           ← 必须，术语定义
  ✅ metaphor-registry.md  ← 必须，避免比喻冲突
  ✅ chXX-report.md        ← 必须，本章研究素材
  ✅ chapter-summaries.md ← 必须，了解前序章节
  ❌ 其他章节的正文        ← 不需要，避免上下文浪费

R1 源码审查员的 File Pointers：
  ✅ chXX-draft.md         ← 待审查的草稿
  ✅ source-map.md         ← 源码文件定位
  ✅ 相关源码文件           ← 验证引用的准确性
  ❌ style-guide.md        ← 不需要，只查代码准确性

2.4.2 静态文件

特点：创建后不再修改，是全书的"宪法"。

文件说明
outline.md最终定稿大纲
source-map.md源码文件→章节映射
style-guide.md写作风格指南

2.4.3 追加文件

特点：只增不删，每章完成后追加新内容。是跨章节连续性的关键。

文件追加时机说明
glossary.md每章完成后新增术语及定义
chapter-summaries.md每章完成后各章 200-300 字摘要
metaphor-registry.md每章完成后新增比喻/类比
cross-references.md每章完成后新增交叉引用点

2.4.4 可覆写文件

特点：每次写入时全量替换，生命周期仅限单章。

文件模式写入者说明
chXX-report.md研究员 #3本章源码分析
chXX-draft.md作家 #4本章初稿
chXX-r1.mdR1源码审查报告
chXX-r2.mdR2一致性审查报告

2.6 信息流向规则

2.6.1 单向通信规则

✅ 主编排 → Agent      （通过 File Pointers 注入任务）
✅ Agent → 文件系统     （写入产出物）
✅ 主编排 ← 文件系统    （读取产出物，决定下一步）
❌ Agent → Agent        （禁止直接通信）
❌ Agent → 主编排       （Agent 不主动发起请求）

为什么禁止 Agent 直接通信？

想象一个剧组的混乱场景：演员 A 突然去找演员 B 讨论剧本，演员 C 听到了也加入讨论，结果导演（主编排）完全不知道发生了什么。这会导致：

  • 信息流向混乱，难以追踪
  • 可能出现环形依赖
  • 上下文污染加剧

2.7 小结

本章我们深入理解了 Scriptorium 的系统架构：

  1. Hub-Spoke 架构：主编排作为唯一中枢，所有 Agent 只与主编排通信
  2. 无状态设计：Agent 不保留记忆，所有状态存储在文件系统中
  3. File Pointers 机制：精确的上下文注入，遵循最小权限原则
  4. 三类文件：静态文件、追加文件、可覆写文件各有明确的生命周期
  5. 12 个 Agent 分工明确：管理组、执行组、审查组各司其职
