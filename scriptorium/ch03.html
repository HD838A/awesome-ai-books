第3章：主编排的秘密

本章目标
  • 理解主编排作为"总导演"的核心职责
  • 掌握主编排的调度机制和工作流程
  • 了解主编排如何管理进度和维护长记忆
  • 理解异常处理和断点恢复策略

3.1 主编排是谁？

想象一个电影剧组：演员们各司其职，但谁来决定"这一幕先拍谁"、"道具准备好了吗"、"这个镜头要不要重拍"？

是导演。

在 Scriptorium 中，主编排就是那个"导演"——它不写内容（不是作家），不审代码（不是审查员），不研究源码（不是研究员）。它只做一件事：协调。

3.1.1 为什么说主编排是"用户自己"？

这是一个有趣的设计选择。在 Scriptorium 中，主编排 不是 作为子 Agent 被调度的，而是直接由用户（AI 助手的主会话）扮演的。

类比
想象你雇了一个"项目管家"。但这个管家不是你的员工，而是你自己——你只是用了管家的手册（QUICK_START.md）来提醒自己该做什么。

为什么不把主编排也做成子 Agent？

因为会陷入"谁来调度调度者"的问题。如果 #0 主编排也是子 Agent，那么谁来调度它？所以最自然的方式是：用户就是主编排。

3.1.2 一句话启动

用户只需要说一句话，就能让整个框架运转起来：

我的项目源码在 /path/to/project。请读 QUICK_START.md，然后向我提问。
没有问题就开始你的工作。

这听起来很简单，但背后是精心设计的一整套流程。主编排会：

  1. 📖 读取 QUICK_START.md 了解框架手册
  2. ❓ 向用户确认基本信息（书名、目标读者等）
  3. 🚀 自主运行全部 5 个阶段
  4. 📚 交付可阅读的 HTML 电子书

3.2 主编排的五大职责

3.2.1 SQL 进度追踪

主编排使用 todos 表管理所有任务状态：

erDiagram todos { string id PK string status "pending/in_progress/done/blocked" string content "任务描述" string priority "high/medium/low" } todo_deps { string todo_id FK string depends_on FK } todos ||--o{ todo_deps : "depends on"

为什么用 SQL 而不是文件？

类比：项目管理用甘特图而不是笔记本。手写的笔记很难追踪依赖关系，但数据库查询可以轻松回答"哪些任务可以开始？"。

-- 查询就绪任务（所有前置依赖已完成）
SELECT t.* FROM todos t
WHERE t.status = 'pending'
AND NOT EXISTS (
    SELECT 1 FROM todo_deps td
    JOIN todos dep ON td.depends_on = dep.id
    WHERE td.todo_id = t.id AND dep.status != 'done'
);

3.2.2 子 Agent 调度

主编排根据依赖关系确定就绪任务，然后构造精确的 prompt 调度对应子 Agent：

flowchart TB O["主编排
查询就绪任务"] --> Q["SQL 查询"] Q --> R["发现就绪任务"] R --> P["构造 Prompt"] P --> A["调度 Agent"] subgraph "Prompt 内容" T["任务目标"] I["📥 输入文件"] O2["📤 输出文件"] G["📎 长记忆"] M["✅ 完成标记"] end P --> T P --> I P --> O2 P --> G P --> M

关键：File Pointers 必须精确

主编排传递给子 Agent 的不是"随便读点什么"，而是精心挑选的文件组合：

📥 输入文件：
   - output/memory/outline.md       ← 大纲（任务范围）
   - output/memory/source-map.md    ← 源码定位
   - 源码文件（根据 source-map）     ← 实际源码

📤 输出文件：
   - output/research/ch03-report.md ← 研究报告

3.2.3 长记忆文件维护

主编排负责维护跨章节共享的"记忆文件"：

文件作用更新时机
chapter-summaries.md各章摘要每章完成后追加
glossary.md术语表每章完成后追加
metaphor-registry.md比喻注册表每章完成后追加
类比
主编排就像项目秘书，维护一份"项目百科"。每个子 Agent 完成任务后，都要往百科里添加新条目。

3.2.4 产出质量审计

主编排不信任任何子 Agent 的输出，必须验证：

  1. 完成标记检查：文件末尾是否包含 <!-- DRAFT_COMPLETE --> 等标记？
  2. 内容质量检查：是否符合质量标准？
  3. 格式检查：是否遵循输出规格？

如果不合格，主编排会：

  • 将具体问题反馈给作家 Agent
  • 要求针对性修改
  • 不通过则重新调度

3.2.5 断点恢复

写作过程中断？告诉 AI：

请读 output/memory/checkpoint.md，继续上次未完成的工作。

主编排会通过双重机制恢复进度：

  1. 扫描 todos 表的状态
  2. 检查文件完成标记
flowchart LR A["中断"] --> B["读取 checkpoint.md"] B --> C["检查 todos 表"] C --> D{"文件完成标记?"} D -->|"存在"| E["继续下一任务"] D -->|"不存在"| F["重新执行"]

3.3 主编排的调度流程

3.3.1 标准调度模板

每次调度子 Agent 前，主编排执行以下流程：

1️⃣ 查询 SQL 确定就绪任务
2️⃣ 确认该任务对应的 Agent 类型
3️⃣ 构造 prompt，包含：
   - 任务目标描述
   - 📥 输入文件列表（精确路径）
   - 📤 输出文件路径及格式要求
   - 📎 需参考的长记忆文件
   - ✅ 完成标记要求
   - ⚠️ 特别注意事项
4️⃣ 调度 Agent 执行
5️⃣ 审查产出 → 更新状态

3.3.2 异常处理策略

场景处理方式
审查不通过将具体问题反馈给作家 Agent，要求针对性修改
子 Agent 输出缺少完成标记判定为未完成，重新调度
连续失败 ≥3 次暂停该任务，标记为 blocked，请求用户介入
长记忆文件冲突以最新完成章节的内容为准，人工确认后更新

3.4 主编排在各阶段的工作

3.4.1 Phase 1 大纲定稿

主编排调用：
  ├── 架构师 #1  → 分析源码，生成 outline.md
  ├── 读者代言人 #2  → 审核大纲
  └── 用户确认  → 最终定稿

3.4.2 Phase 2 共享资源构建

主编排直接执行：
  ├── 创建 style-guide.md
  ├── 创建 glossary.md
  ├── 创建 metaphor-registry.md
  └── 创建 chapter-summaries.md（空模板）

3.4.3 Phase 3 逐章写作

这是主编排最忙碌的阶段：

每章 4 步流水线：

Step 1  研究  → 调度研究员 #3
Step 2  写作  → 调度作家 #4
Step 3  三审  → 调度 R1/R2/R3（并行）
Step 4  评审  → 调度 RS/RE/RH（并行）

3.4.4 Phase 4 统稿审计

主编排对全书进行最终审计：

  • 术语一致性检查
  • 跨章引用完整性
  • 代码片段准确性
  • 整体叙事连贯性

3.4.5 Phase 5 装帧发布

主编排调度：
  ├── 装帧工人 #11  → 生成 HTML
  └── 质检员 #12   → 程序化质检

3.5 主编排的"日工作计划"

如果我们把主编排想象成一个真实的人，它的一天是这样的：

08:00 上班，看一眼 checkpoint.md（今天的任务清单）
08:05 看看有哪些任务"就绪"了（前置依赖都完成了）
08:10 给研究员 #3 发邮件："请调研第4章的源码"
09:30 收到研究员的研究报告，质量不错，归档
09:35 给作家 #4 发邮件："请写第4章，用这份报告做素材"
11:00 收到作家的初稿，打回修改："代码块超长了"
12:00 收到修改稿，这次合格了
12:05 同时发给 R1/R2/R3："请并行审查这份草稿"
14:00 收到三份审查报告，汇总
14:05 同时发给 RS/RE/RH："请三视角评审"
16:00 收到读者评审团反馈，都是小问题
16:30 给作家发邮件："按反馈修改第4章"
17:30 第4章最终稿归档，更新 checkpoint.md
17:35 看看第5章能不能开始了...
核心洞察
主编排不做任何"创作"工作——不写代码、不写文字、不做研究。它的价值在于：知道谁该做什么，什么时候做，以及产出合不合格。

3.6 小结

本章我们深入理解了主编排（Orchestrator）的工作机制：

  1. 主编排是"总导演"：协调所有子 Agent，不做具体创作
  2. SQL 追踪进度：用 todos 表管理任务状态和依赖关系
  3. 精确调度：每次调度都要构造包含 File Pointers 的精确 prompt
  4. 质量审计：不信任子 Agent 输出，必须验证完成标记和质量
  5. 断点恢复：通过 checkpoint.md 和文件完成标记实现任意中断恢复
