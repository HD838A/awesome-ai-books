第 3 章：核心概念

认识四大支柱

上一章我们快速上手了框架，跑通了一个多 Agent 协作的例子。现在，让我们深入理解这个框架的四大核心概念：

  • Agent — AI 员工
  • Task — 工作指令卡
  • Team — 项目组
  • Orchestrator — 总指挥

💡 比喻提醒

想象你在管理一个软件项目团队：Team 就是项目组，Agent 是团队成员，Task 是工作卡，Orchestrator 是分配任务、协调进度的项目经理。

3.1 Agent：AI 员工

3.1.1 Agent 是什么？

在 Open Multi-Agent 框架中，Agent 是一个封装了"角色 + 模型 + 工具"的执行单元。

const agent: AgentConfig = {
  name: 'researcher',                    // 员工编号
  model: 'claude-sonnet-4-6',           // 使用什么 AI 模型
  systemPrompt: '你是一个专业研究员...', // 员工的"性格"和"能力"
  tools: ['bash', 'file_read'],         // 员工能用的工具
}

就像一个真实的员工：

  • 有自己的专业领域（systemPrompt）
  • 会使用工具完成任务（tools）
  • 需要明确的目标（prompt）
  • 会消耗资源（Token）

3.1.2 Agent 的三层抽象

框架对 Agent 实现了三层抽象：

对话循环 + 工具调用"] end subgraph "第一层: LLMAdapter" L["LLMAdapter

层级说明用户接触
----------------------
高级 APIrun()、prompt()、stream()✅ 直接使用
AgentRunner对话循环、工具调用编排❌ 内部使用
LLMAdapter与 LLM API 通信❌ 内部使用

3.1.3 三种执行方式

方式 1：run() — 一次性任务

const result = await agent.run('写一个快速排序算法')

// 特点：每次都是新对话，历史不保留
// 适用：独立的一次性任务

方式 2：prompt() — 多轮对话

const result1 = await agent.prompt('解释什么是闭包')
const result2 = await agent.prompt('能举个代码例子吗')  // 上下文包含上一轮

// 特点：累积对话历史
// 适用：需要上下文的交互场景

方式 3：stream() — 流式输出

for await (const event of agent.stream('给我讲个故事')) {
  if (event.type === 'text') {
    process.stdout.write(event.data)
  }
}

// 特点：实时看到输出，无需等待完成
// 适用：长文本生成、实时展示

3.1.4 Agent 的状态

Agent 内部维护自己的状态：

stateDiagram-v2 [*] --> idle idle --> running: run() / prompt() running --> completed: 成功完成 running --> error: 执行出错 completed --> idle: reset() error --> idle: reset()
interface AgentState {
  status: 'idle' | 'running' | 'completed' | 'error'
  messages: LLMMessage[]    // 对话历史
  tokenUsage: TokenUsage    // 资源消耗
}

3.1.5 关键配置项

const config: AgentConfig = {
  name: 'my-agent',              // 唯一标识符
  model: 'claude-sonnet-4-6',   // LLM 模型
  provider: 'anthropic',         // 提供商（可省略，自动推断）
  systemPrompt: '...',          // 角色定义（关键！）
  tools: ['bash', 'file_write'], // 可用工具
  maxTurns: 10,                  // 最大对话轮次
  temperature: 0.3,              // 输出随机性
  maxTokens: 4096,              // 最大输出 token
  apiKey: '...',                // 可覆盖默认 API Key
  baseURL: '...',               // 自定义 API 地址
}

💡 systemPrompt 编写技巧

systemPrompt 决定了 Agent 的"性格"。好的 prompt 应该：

1. 明确角色：告诉 Agent"你是什么"

2. 定义能力：告诉它"你能做什么"

3. 设定风格：告诉它"你怎么做"

```typescript

systemPrompt: `你是一个资深的 TypeScript 开发者。

你擅长编写简洁、高效、类型安全的代码。

当需要实现功能时，你会先分析需求，再写代码。

代码风格遵循 Airbnb TypeScript 规范。`

```

3.2 Task：工作指令卡

3.2.1 Task 是什么？

如果说 Agent 是"人"，那 Task 就是"工作指令卡"。它描述了一项具体工作：

interface Task {
  id: string                     // 唯一标识（UUID）
  title: string                  // 任务名称
  description: string            // 详细描述
  status: TaskStatus            // 状态
  assignee?: string              // 负责人（Agent 名）
  dependsOn?: string[]          // 依赖哪些任务
  result?: AgentRunResult       // 执行结果
}

3.2.2 Task 的生命周期

┌─────────┐     assign      ┌─────────┐     finish      ┌───────────┐
│ pending │ ──────────────► │ running │ ──────────────► │ completed │
└─────────┘                 └─────────┘                 └───────────┘
     │                            │                            ▲
     │                            │ error                      │
     │                            ▼                            │
     │                      ┌─────────┐                        │
     └──────────────────────►│ failed  │────────────────────────┘
                             └─────────┘      retry / dependsOn

3.2.3 创建 Task

import { createTask } from '@jackchen_me/open-multi-agent'

const task = createTask({
  title: '设计数据库',
  description: '为用户系统设计数据库结构，包括 users 表和权限表',
  assignee: 'architect',
  dependsOn: [],           // 没有依赖，最先执行
})

const task2 = createTask({
  title: '实现 API',
  description: '根据设计实现 REST API 接口',
  assignee: 'developer',
  dependsOn: [task.id],   // 依赖"设计数据库"
})

3.2.4 依赖检查

框架提供了 isTaskReady() 函数来判断任务是否可以开始：

import { isTaskReady } from '@jackchen_me/open-multi-agent'

// 任务就绪条件：
// 1. 状态是 'pending'
// 2. 所有依赖任务都已 'completed'

if (isTaskReady(task2, allTasks)) {
  console.log('可以开始执行任务2了！')
}

3.2.5 拓扑排序

当有多个任务时，框架自动计算执行顺序：

import { getTaskDependencyOrder } from '@jackchen_me/open-multi-agent'

const tasks = [task1, task2, task3, task4]
const ordered = getTaskDependencyOrder(tasks)

// 返回顺序保证：
// - 依赖任务排在前面
// - 独立任务并行执行
graph LR subgraph "原始任务" A["task1"] --> B["task2"] A --> C["task3"] B --> D["task4"] C --> D end subgraph "执行顺序" E["task1"] --> F["task2, task3 (并行)"] F --> G["task4"] end

3.3 Team：项目组

3.3.1 Team 是什么？

Team 是 Agent 的容器，提供了：

  • Agent 注册：团队有哪些成员
  • 共享内存：成员之间共享数据
  • 消息总线：成员之间传递消息
  • 任务队列：管理待执行任务
  • 事件系统：监听团队状态变化

3.3.2 创建 Team

const team = orchestrator.createTeam('dev-team', {
  name: 'dev-team',
  agents: [architect, developer, reviewer],
  sharedMemory: true,           // 启用共享内存
  maxConcurrency: 3,            // 最大并发数
})

3.3.4 监听团队事件

team.on('task:complete', (data) => {
  const event = data as OrchestratorEvent
  console.log(`任务完成: ${event.task}`)
})

team.on('task:failed', (data) => {
  const event = data as OrchestratorEvent
  console.error(`任务失败: ${event.task}`)
})

team.on('agent:start', (data) => {
  const event = data as OrchestratorEvent
  console.log(`Agent 启动: ${event.agent}`)
})

3.4 Orchestrator：总指挥

3.4.1 Orchestrator 是什么？

Orchestrator 是整个框架的核心，它：

  1. 管理 Team：创建、销毁团队
  2. 协调 Agent：分配任务、收集结果
  3. 调度 Task：根据依赖关系安排执行
  4. 处理异常：优雅失败、重试机制
  5. 汇总输出：将多个 Agent 的结果整合

3.4.2 Orchestrator 的核心方法

// 创建团队
const team = orchestrator.createTeam('team-name', teamConfig)

// 运行单个 Agent
const result = await orchestrator.runAgent(agentConfig, prompt)

// 运行团队
const result = await orchestrator.runTeam(team, goal)

// 运行任务队列
const result = await orchestrator.runTasks(tasks, agents)

3.4.3 核心配置

const orchestrator = new OpenMultiAgent({
  defaultModel: 'claude-sonnet-4-6',  // 默认模型
  maxConcurrency: 5,                   // 最大并发
  onProgress: (event) => {},           // 进度回调
  onTrace: (trace) => {},              // 追踪回调
})

3.6 从一个例子看协作

const orchestrator = new OpenMultiAgent()

// 创建团队
const team = orchestrator.createTeam('dev', {
  name: 'dev',
  agents: [
    { name: 'architect', systemPrompt: '你负责设计...', tools: [...] },
    { name: 'developer', systemPrompt: '你负责写代码...', tools: [...] },
  ],
  sharedMemory: true,
})

// 运行团队，描述目标
const result = await orchestrator.runTeam(team, '创建一个 TODO 应用')

// 框架内部发生了什么：
// 1. Orchestrator 创建临时 Coordinator
// 2. Coordinator 分析目标，分解成 Task DAG
// 3. Scheduler 根据依赖调度 Task
// 4. AgentPool 并行运行 Agent
// 5. 结果汇总到 Coordinator
// 6. 返回最终结果

本章小结

  1. Agent 是执行单元，封装了模型、角色和工具，提供 run()、prompt()、stream() 三种执行方式。
  1. Task 是工作指令卡，有状态（pending→running→completed/failed）和依赖关系（dependsOn）。
  1. Team 是 Agent 的容器，提供共享内存、消息总线、任务队列等协作基础设施。
  1. Orchestrator 是总指挥，协调 Team、Agent、Task 的一切运作。
  1. 四者关系：Orchestrator 管理 Team，Team 包含 Agent，Agent 执行 Task。

思考题

  1. 为什么 prompt() 会累积对话历史，而 run() 不会？各自适合什么场景？
  1. 如果一个 Task 的所有依赖都失败了，这个 Task 应该怎么处理？被标记为什么状态？
  1. Team 中的 sharedMemory 和 messageBus 有什么区别？什么时候用哪个？
