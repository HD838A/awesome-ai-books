第 4 章：任务调度与依赖管理

任务调度的艺术

想象你是一个项目经理，手里有一堆工作指令卡（Task），还有几个员工（Agent）。你需要决定：

  • 谁来做？ 分配问题
  • 什么时候做？ 顺序问题
  • 做不完怎么办？ 并发问题

这就是任务调度要解决的问题。

4.1 Task 的完整生命周期

4.1.2 创建任务

import { createTask } from '@jackchen_me/open-multi-agent'

const task1 = createTask({
  title: '设计 API 结构',
  description: '为 TODO 应用设计 REST API endpoints',
  assignee: 'architect',
})

const task2 = createTask({
  title: '实现后端',
  description: '使用 Express.js 实现后端逻辑',
  assignee: 'developer',
  dependsOn: [task1.id],  // 等待 task1 完成
})

const task3 = createTask({
  title: '编写测试',
  description: '为后端 API 编写单元测试',
  assignee: 'tester',
  dependsOn: [task2.id],  // 等待 task2 完成
})

4.1.3 Task 的属性

interface Task {
  id: string
  title: string
  description: string
  status: 'pending' | 'in_progress' | 'completed' | 'failed' | 'skipped'
  assignee?: string
  dependsOn?: string[]     // 依赖的任务 ID 列表
  result?: string           // 执行结果
  maxRetries?: number       // 最大重试次数
  retryDelayMs?: number     // 重试延迟（毫秒）
  retryBackoff?: number     // 退避系数（如 2 = 指数退避）
}

4.2 TaskQueue：依赖感知的任务队列

4.2.1 为什么需要 TaskQueue？

普通数组无法处理依赖关系：

// ❌ 简单数组的问题
const tasks = [task1, task2, task3]
// 如果 task2 依赖 task1，你必须手动检查 task1 是否完成
// 才能决定是否可以执行 task2

TaskQueue 帮你自动处理这些：

import { TaskQueue } from '@jackchen_me/open-multi-agent'

const queue = new TaskQueue()

// 添加任务时，TaskQueue 自动检查依赖
queue.add(task1)  // 状态: pending
queue.add(task2)  // 状态: blocked（因为 task1 未完成）
queue.add(task3)  // 状态: blocked（因为 task2 未完成）

4.2.2 事件驱动

TaskQueue 会在状态变化时触发事件：

queue.on('task:ready', (task) => {
  console.log(`任务 "${task.title}" 可以开始执行了！`)
  scheduleToAgent(task)
})

queue.on('task:complete', (task) => {
  console.log(`任务 "${task.title}" 已完成`)
})

queue.on('task:failed', (task) => {
  console.error(`任务 "${task.title}" 失败了: ${task.result}`)
})

queue.on('all:complete', () => {
  console.log('所有任务完成！')
})

4.2.3 complete() 的自动解封

// 任务 1 完成后，任务 2 和 3 会自动解封
queue.complete(task1.id)

// TaskQueue 内部发生了什么：
// 1. task1 状态 → completed
// 2. 检查 task2: dependsOn 包含 task1.id ✓ → status → pending，触发 'task:ready'
// 3. 检查 task3: dependsOn 包含 task2.id，但 task2 还是 blocked → 等待

4.2.4 级联失败

当一个任务失败时，所有依赖它的任务都会被标记为失败：

graph TD A["task1: 设计\n✅ completed"] --> B["task2: 开发\n❌ failed"] B --> C["task3: 测试\n⛔ skipped (cascade)"] B --> D["task4: 部署\n⛔ skipped (cascade)"] E["task5: 文档\n⛔ skipped (cascade)"] B --> E
queue.fail(task2.id, '数据库连接失败')

// 级联效果：
// - task2: failed
// - task3: skipped（上游失败，无法执行）
// - task4: skipped
// - task5: skipped

4.3 调度策略

4.3.1 四种策略一览

策略名称核心逻辑适用场景
--------------------------------
round-robin轮询顺序分配，循环使用负载均衡
least-busy最空闲优先选择任务最少的 Agent资源平衡
capability-match能力匹配关键词匹配最合适的 Agent专业化分工
dependency-first依赖优先关键路径优先多步骤流水线（默认）

4.3.2 轮询策略（round-robin）

最简单的策略：任务轮流分配给 Agent。

const scheduler = new Scheduler('round-robin')

const tasks = [task1, task2, task3, task4]
const agents = [agentA, agentB]

const assignments = scheduler.schedule(tasks, agents)
// task1 → agentA
// task2 → agentB
// task3 → agentA
// task4 → agentB

4.3.3 最空闲优先（least-busy）

选择当前负载最轻的 Agent：

const scheduler = new Scheduler('least-busy')

// Agent A 正在执行 2 个任务，Agent B 正在执行 0 个
const assignments = scheduler.schedule(tasks, [agentA, agentB])
// 新任务会优先分配给 Agent B

4.3.4 能力匹配（capability-match）

根据任务的关键词匹配最合适的 Agent：

const agents = [
  { name: 'architect', systemPrompt: 'You design system architecture...' },
  { name: 'developer', systemPrompt: 'You write clean code...' },
  { name: 'reviewer', systemPrompt: 'You review code quality...' },
]

const scheduler = new Scheduler('capability-match')

const task = createTask({
  title: '设计数据库',
  description: 'Design a PostgreSQL schema for user management',
})

const assignments = scheduler.schedule([task], agents)
// architect 的 systemPrompt 包含 "architecture"
// 与 task 的 "Design" 关键词匹配 → 分配给 architect

4.3.5 依赖优先（dependency-first，默认）

这是框架的杀手锏。

核心思想：优先完成"阻塞最多其他任务"的关键路径任务。

const scheduler = new Scheduler('dependency-first')

// 任务依赖关系：
// taskA (无依赖)
// taskB (依赖 taskA)
// taskC (依赖 taskA)
// taskD (依赖 taskB 和 taskC)

// 关键度分析：
// - taskA: 被 B、C、D 依赖 → 关键度 = 3
// - taskB: 被 D 依赖 → 关键度 = 1
// - taskC: 被 D 依赖 → 关键度 = 1
// - taskD: 无依赖 → 关键度 = 0

// 分配顺序：taskA 最先分配（关键度最高）
const assignments = scheduler.schedule([taskD, taskC, taskB, taskA], agents)
// 实际顺序: taskA → taskB → taskC → taskD（按关键度排序）

4.4 并发控制：Semaphore

4.4.1 问题

当你有 10 个 Agent，但只想同时运行 3 个时，怎么办？

4.4.2 答案：Semaphore 信号量

把它想象成停车场的闸机：

  • 闸机有 N 个车位（maxConcurrency）
  • 每辆车进入时占用一个车位
  • 车位满时，后面的车排队等待
  • 有车离开时，下一辆车进入
import { Semaphore } from '@jackchen_me/open-multi-agent'

const semaphore = new Semaphore(3)  // 最多同时 3 个

async function runTask(task) {
  await semaphore.acquire()  // 等待车位
  try {
    return await execute(task)
  } finally {
    semaphore.release()  // 释放车位
  }
}

4.4.3 自动释放

// 使用 run() 方法自动处理获取和释放
const result = await semaphore.run(async () => {
  return await agent.run(prompt)
})
// 不管成功还是失败，信号量都会被释放

4.5 AgentPool：Agent 并发池

4.5.1 AgentPool 是什么？

AgentPool 是 Agent 的容器，提供了注册、调度、执行的一站式服务：

import { AgentPool } from '@jackchen_me/open-multi-agent'

const pool = new AgentPool(3)  // 最多同时 3 个 Agent

pool.add(agentA)
pool.add(agentB)
pool.add(agentC)

// 运行单个 Agent
const result = await pool.run('architect', '设计一个 API')

// 并行运行多个
const results = await pool.runParallel([
  { agent: 'architect', prompt: '设计 API' },
  { agent: 'developer', prompt: '实现 API' },
  { agent: 'reviewer', prompt: '审查代码' },
])

// 轮询选择任意 Agent
const result = await pool.runAny('处理一个随机任务')

4.5.2 并发控制原理

maxConcurrency = 3

时间 ──────────────────────────────────────────────────────►

Agent1: ████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
Agent2: ░░░░████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
Agent3: ░░░░░░░░░░░░░░░░████████░░░░░░░░░░░░░░░░░░░░░░░░░

        ^          ^         ^         ^
        T1         T2        T3        T4（需要等待）

4.5.3 runParallel 的容错

const results = await pool.runParallel([
  { agent: 'architect', prompt: '设计 API' },
  { agent: 'developer', prompt: '实现 API' },  // 这个可能失败
  { agent: 'reviewer', prompt: '审查代码' },
])

// 即使 developer 失败，architect 和 reviewer 仍然会执行
// 失败的 Agent 结果会包含在 Map 中
const devResult = results.get('developer')
if (!devResult.success) {
  console.error('开发者任务失败:', devResult.output)
}

4.6 综合示例

4.6.1 完整流程

import {
  OpenMultiAgent,
  TaskQueue,
  Scheduler,
  createTask,
} from '@jackchen_me/open-multi-agent'

const orchestrator = new OpenMultiAgent()

// 1. 创建团队
const team = orchestrator.createTeam('dev-team', {
  name: 'dev-team',
  agents: [architect, developer, reviewer],
  sharedMemory: true,
})

// 2. 创建任务队列
const queue = new TaskQueue()

// 3. 监听事件
queue.on('task:ready', (task) => {
  const scheduler = new Scheduler('dependency-first')
  scheduler.autoAssign(queue, team.getAgents())
})

queue.on('task:complete', (task) => {
  console.log(`✅ ${task.title} 完成`)
})

queue.on('all:complete', () => {
  console.log('🎉 所有任务完成！')
})

// 4. 添加任务
queue.addBatch([
  createTask({ title: '设计', assignee: 'architect', dependsOn: [] }),
  createTask({ title: '开发', assignee: 'developer', dependsOn: ['design-id'] }),
  createTask({ title: '审核', assignee: 'reviewer', dependsOn: ['dev-id'] }),
])

// 5. 手动触发第一个任务的执行
const readyTask = queue.list().find(t => t.status === 'pending')
if (readyTask) {
  const result = await orchestrator.runAgent(
    { name: readyTask.assignee!, ... },
    readyTask.description
  )
  queue.complete(readyTask.id, result.output)
}

4.7 调度策略对比

                    简单场景                    复杂流水线
                         │                        │
          ┌───────────────┼───────────────┐        │
          ▼               ▼               ▼        ▼
      round-robin    least-busy   capability-match  dependency-first
          │               │               │            │
          ▼               ▼               ▼            ▼
      轮询分配        负载均衡      专业化分工      关键路径优先 ← 推荐

推荐原则：

  • 简单任务 → round-robin
  • 负载敏感 → least-busy
  • 专业分工 → capability-match
  • 复杂流水线 → dependency-first（默认）

本章小结

  1. Task 状态机：pending → in_progress → completed/failed/skipped
  1. TaskQueue 自动处理依赖：完成一个任务后，自动解封依赖它的任务。
  1. 级联失败：上游失败会级联影响所有下游任务，防止它们永远阻塞。
  1. 四种调度策略：
  • round-robin：轮询分配
  • least-busy：选择最空闲 Agent
  • capability-match：关键词匹配最合适的 Agent
  • dependency-first：关键路径优先（默认）
  1. Semaphore 是并发控制的核心，限制同时运行的任务数量。
  1. AgentPool 封装了 Agent 注册、调度、执行，提供 runParallel() 等高级 API。

思考题

  1. 如果 taskB 依赖 taskA，taskC 同时依赖 taskA 和 taskB，那么 taskC 何时会从 blocked 变为 pending？
  1. 为什么 dependency-first 是默认策略？考虑一个 10 步的流水线，如果关键任务被延迟会怎样？
  1. Semaphore 的 acquire() 返回 Promise。这在 Node.js 的单线程模型中是如何工作的？
