学完这章，你将能够：

7.1 为什么需要多 Agent 协作？



7.1.1 单 Agent 的局限



一个 Agent 就像一个全栈工程师：

优点局限

✅ 通才，什么都能做❌ 每个任务都是串行执行
✅ 上下文连贯❌ 复杂任务容易"迷失"
✅ 工具齐全❌ Token 消耗大

7.1.2 多 Agent 的优势



多 Agent 协作就像一个专业团队：

┌─────────────────────────────────────────────────────────────────┐

│                        团队协作模式                               │

├─────────────────────────────────────────────────────────────────┤

│                                                                 │

│    【产品经理 Agent】                                            │

│    接收需求，拆解任务，协调各方                                  │

│                                                                 │

│    ┌─────────┐    ┌─────────┐    ┌─────────┐                     │

│    │ 前端    │    │ 后端    │    │ 测试    │                     │

│    │ Agent   │ +  │ Agent   │ +  │ Agent   │                     │

│    └─────────┘    └─────────┘    └─────────┘                     │

│                                                                 │

│    各自专注领域，并行工作，输出专业成果                           │

│                                                                 │

└─────────────────────────────────────────────────────────────────┘




7.2 ACP 协议概述



7.2.1 什么是 ACP？



ACP（Agent Client Protocol） 是 Hermes Agent 的多 Agent 通信协议：

┌─────────────────────────────────────────────────────────────────┐

│                       ACP 协议栈                                 │

├─────────────────────────────────────────────────────────────────┤

│                                                                 │

│  【应用层】                                                      │

│  ├── Editor 集成（VS Code、Zed、JetBrains）                       │

│  ├── CLI 交互                                                    │

│  └── 消息平台（需要时）                                          │

│                                                                 │

│  【协议层】 ACP                                                  │

│  ├── JSON-RPC 通信                                               │

│  ├── 工具调用传递                                               │

│  └── 会话管理                                                    │

│                                                                 │

│  【传输层】 stdio / HTTP / WebSocket                             │

│                                                                 │

└─────────────────────────────────────────────────────────────────┘


7.2.2 ACP 的两种模式



模式用途特点

委派模式（Delegation）一个 Agent 委派子 Agent共享进程，通过函数调用
服务端模式（ACP Server）编辑器集成通过 stdio 通信



7.3 委派模式详解



7.3.1 delegate_task 工具



delegate_task 是 Hermes Agent 的核心委派工具：

delegate_task(

    goal: str,                          # 子 Agent 的任务目标

    context: str = "",                   # 上下文信息

    toolsets: List[str] = None,         # 工具集，默认为 ["terminal", "file", "web"]

    tasks: List[Dict] = None,           # 批量模式：并行执行多个子任务

    max_iterations: int = 50,            # 最大迭代次数

    acp_command: str = None,            # ACP 命令

    acp_args: List[str] = None          # ACP 参数

)


7.3.2 子 Agent 的特性



┌─────────────────────────────────────────────────────────────────┐

│                     子 Agent 隔离环境                            │

├─────────────────────────────────────────────────────────────────┤

│                                                                 │

│  ✅ 独立对话历史（无父 Agent 上下文）                            │

│  ✅ 独立终端会话（独立的工作目录）                                │

│  ✅ 受限工具集（安全隔离）                                        │

│  ✅ 独立系统提示（专注任务）                                       │

│                                                                 │

│  ❌ 不能调用 delegate_task（防止递归）                            │

│  ❌ 不能调用 clarify（不能与用户交互）                            │

│  ❌ 不能写 memory（防止冲突）                                     │

│  ❌ 不能调用 send_message（防止跨平台副作用）                      │

│  ❌ 不能调用 execute_code（需逐步推理而非写脚本）                  │

│                                                                 │

└─────────────────────────────────────────────────────────────────┘


7.3.3 委派流程



用户: "帮我研究三个主题"



───────────────────────────────────────────────────────────────────



【父 Agent】

│

├── 分析任务，拆分为三个子任务

│

├── 启动 3 个子 Agent（并行）

│   ├── 子 Agent 1: 研究 WebAssembly

│   ├── 子 Agent 2: 研究 RISC-V

│   └── 子 Agent 3: 研究量子计算

│

├── 等待子 Agent 完成（最多 50 轮迭代）

│

└── 汇总结果，返回给用户



───────────────────────────────────────────────────────────────────




7.4 实战：并行研究模式



7.4.1 场景



研究三个主题，返回结构化报告：

用户：请帮我研究这三个技术趋势：


  • WebAssembly 在浏览器外的应用
  • RISC-V 服务器芯片的采用情况
  • 量子计算的实际应用




请重点关注最近的进展和主要参与者。


7.4.2 实现



delegate_task(tasks=[

    {

        "goal": "研究 WebAssembly 在 2025 年的浏览器外应用",

        "context": """重点关注：

        - Wasmtime、Wasmer 等运行时的进展

        - 云端/边缘计算用例

        - WASI 标准进展

        请搜索最新资料，整理关键发现。""",

        "toolsets": ["web"]

    },

    {

        "goal": "研究 RISC-V 服务器芯片采用情况",

        "context": """重点关注：

        - 已出货的服务器芯片

        - 云服务商采用情况

        - 软件生态系统

        请搜索最新资料，整理关键发现。""",

        "toolsets": ["web"]

    },

    {

        "goal": "研究量子计算的实际应用",

        "context": """重点关注：

        - 纠错技术突破

        - 实际商业用例

        - 主要公司和研究机构

        请搜索最新资料，整理关键发现。""",

        "toolsets": ["web"]

    }

])


7.4.3 优势



对比串行研究并行委派

时间3x1x
Token 消耗全部在主上下文仅汇总在主上下文
上下文混杂清晰隔离



7.5 实战：代码审查模式



7.5.1 场景



对认证模块进行安全审查：

用户：请帮我审查 src/auth/ 目录的认证模块，

检查 SQL 注入、JWT 验证、密码处理和会话管理问题。

如果发现 bug，请修复并运行测试。


7.5.2 实现



delegate_task(

    goal="审查 src/auth/ 目录的安全问题并修复",

    context="""项目位置：/home/user/webapp

技术栈：Python 3.11, Flask, PyJWT, bcrypt



认证相关文件：


  • src/auth/login.py
  • src/auth/jwt.py
  • src/auth/middleware.py




测试命令：pytest tests/auth/ -v



重点检查：


  • SQL 注入漏洞
  • JWT 验证问题
  • 密码哈希处理
  • 会话管理安全




请修复发现的问题并验证测试通过。""",

    toolsets=["terminal", "file"]

)


7.5.3 关键：上下文传递



⚠️ 重要：子 Agent 完全不知道父 Agent 的对话内容。如果你说"修复我们讨论的那个 bug"，子 Agent 不知道是哪个 bug。



必须明确传递的信息：

信息类型示例

文件路径/home/user/webapp/src/auth/login.py
项目结构Python 3.11, Flask, PyJWT
测试命令pytest tests/auth/ -v
错误信息AttributeError: 'NoneType' has no attribute 'token'



7.6 实战：多文件重构模式



7.6.1 场景



重构 API 服务器的响应格式：

用户：帮我重构整个 API 服务器的响应格式，

需要更新：


  • 所有端点处理器
  • 客户端 SDK
  • API 文档


7.6.2 实现



delegate_task(tasks=[

    {

        "goal": "重构所有 API 端点处理器",

        "context":"""项目：/home/user/api-server

文件：src/handlers/users.py, src/handlers/auth.py, src/handlers/billing.py

旧格式：{"data": result, "status": "ok"}

新格式：{"data": result, "status": 200, "message": "success"}

导入：from src.responses import APIResponse

测试：pytest tests/handlers/ -v""",

        "toolsets": ["terminal", "file"]

    },

    {

        "goal": "更新客户端 SDK",

        "context":"""项目：/home/user/api-server

文件：sdk/python/client.py, sdk/python/models.py

更新 SDK 中的响应解析逻辑以适应新格式

测试：pytest sdk/python/tests/ -v""",

        "toolsets": ["terminal", "file"]

    },

    {

        "goal": "更新 API 文档",

        "context":"""项目：/home/user/api-server

文档位置：docs/api/

格式：Markdown + 代码示例

更新所有响应示例为新格式

在 docs/api/overview.md 添加响应格式说明""",

        "toolsets": ["terminal", "file"]

    }

])




7.7 委派的限制与最佳实践



7.7.1 委派限制



# 子 Agent 被禁止使用的工具

DELEGATE_BLOCKED_TOOLS = frozenset([

    "delegate_task",   # 禁止递归委派

    "clarify",         # 禁止与用户交互

    "memory",          # 禁止写共享记忆

    "send_message",    # 禁止跨平台副作用

    "execute_code",    # 应该逐步推理

])


7.7.2 最佳实践



场景建议

并行研究独立主题用并行委派，节省时间
代码审查用 fresh context 避免偏见
复杂重构按模块拆分，每个子 Agent 负责一部分
需要与用户交互❌ 不能委派，父 Agent 自己处理

7.7.3 性能控制



# 最大并发子 Agent 数（默认 3）

_MAX_CONCURRENT_CHILDREN = 3




最大委派深度（默认 2）



父(0) → 子(1) → 孙(2) → 拒绝


MAX_DEPTH = 2

⭐ 重点回顾



  • ACP（Agent Client Protocol） 是 Hermes Agent 的多 Agent 通信协议
  • delegate_task 工具允许父 Agent 委派子 Agent 执行任务
  • 子 Agent 有隔离的上下文和受限的工具集，安全且高效
  • 并行委派可以显著减少任务时间和上下文 Token 消耗
  • ACP 编辑器集成让 Hermes 可以在 VS Code、Zed、JetBrains 中运行
